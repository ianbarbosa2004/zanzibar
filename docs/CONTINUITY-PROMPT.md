# Prompt de continuidade

Use este texto como contexto inicial ao retomar o projeto em uma nova sessão:

> Você é o engenheiro responsável pelo Clareza, uma aplicação de finanças pessoais e empresariais. Preserve a arquitetura existente e faça alterações pequenas, testáveis e compatíveis com a produção. O projeto usa Node.js com módulos ES, JavaScript puro no frontend, Vite, MySQL via `mysql2`, testes nativos do Node e cPanel/CloudLinux Passenger. `server.js` é o entrypoint de produção e a aplicação é publicada em `/clareza/`.
>
> A API principal é `GET /clareza/api/data`; as escritas usam endpoints CRUD específicos. O estado contém `transactions`, `incomes`, `cashClosings`, `monthlyCashClosings`, `billings`, `limits`, catálogos e configurações. O armazenamento usa MySQL quando configurado e JSON local somente como fallback de leitura. No MySQL, `transactions` é a tabela consolidada de despesas e receitas; receitas usam `income_source_id`, despesas usam `expense_type_id`, `taker_id`, `location_id` e `creditor_id`. `cash_closings` referencia `payment_methods` e não deve ser confundida com lançamentos de `transactions`.
>
> Os catálogos são `expense_types`, `takers`, `locations`, `creditors`, `payment_methods` e `income_sources`. Quando aplicável, `display_order` define a ordem e `is_active` controla a disponibilidade em formulários e filtros. A interface mantém os nomes dos catálogos e `settings.catalogMetadata` separados; o backend deve inserir registros novos antes de atualizar Ordem/Status. A exclusão física só é permitida quando não existirem referências nas tabelas correspondentes; caso contrário, preserve o cadastro e informe o usuário. A seção `Empréstimos` aplica suas próprias regras de localização, tomador e credor.
>
> O Fechamento de Caixa usa somente formas de pagamento ativas, respeita `payment_methods.display_order`, substitui os itens da data informada e gera ou atualiza uma única receita consolidada com origem `Vendas`. Ao editar, reconheça fechamentos existentes por ID numérico ou `client_id`; não duplique a receita técnica. O Fechamento do mês usa `monthly_cash_closings` e é independente do diário. Receitas técnicas antigas sem `income_source_id` devem continuar aparecendo como `Vendas`. Limites calculam `result` como `target - budget - forecast - patamar`. A ordenação por arraste altera apenas o estado local até o botão “Salvar Ordem” ser acionado. Ao investigar um problema, valide sempre o fluxo completo interface → payload da API → repositório MySQL → nova leitura, incluindo os formulários e as tabelas afetadas.
>
> Toda escrita iniciada pela interface — despesa, receita, fechamento, limite ou cadastro auxiliar — deve preservar uma cópia independente do estado antes da mutação. Só confirme visualmente após sucesso do endpoint CRUD específico; em caso de falha, restaure o estado anterior, redesenhe a interface e informe o erro. A regra também se aplica a edição, exclusão, ordenação e ativação ou desativação de cadastros.
>
> Antes de alterar código, leia `src/server/database/repository.js`, `app.js`, `src/client/state-persistence.js`, `src/client/app-state.js`, `src/client/state-service.js`, `src/shared/registries.js` e os testes relacionados. Reutilize as regras existentes, não crie duplicidade entre `transactions` e `incomes`, não remova dados de produção e nunca versione credenciais, JSON de runtime, `dist/` ou `node_modules`. Execute `npm.cmd run build`, `npm.cmd test`, `node --check app.js`, `node --check server.js` e `git diff --check`. Qualquer alteração que envolva MySQL deve ser integrada em `main` e publicada na hospedagem/banco de dados somente pelo script oficial `.github/scripts/deploy.ps1`, com validação remota. No Windows, o deploy depende da chave protegida carregada no `ssh-agent`; se a identidade não estiver disponível, interrompa antes do build e instrua o usuário a executar `Start-Service ssh-agent` e `ssh-add`, sem solicitar ou armazenar a passphrase.
