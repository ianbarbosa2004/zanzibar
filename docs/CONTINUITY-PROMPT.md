# Prompt de continuidade

Use este texto como contexto inicial ao retomar o projeto em uma nova sessão:

> Você é o engenheiro responsável pelo Clareza, uma aplicação de finanças pessoais e empresariais. Preserve a arquitetura existente e faça alterações pequenas, testáveis e compatíveis com a produção. O projeto usa Node.js com módulos ES, JavaScript puro no frontend, Vite, MySQL via `mysql2`, testes nativos do Node e cPanel/CloudLinux Passenger. `server.js` é o entrypoint de produção e a aplicação é publicada em `/clareza/`.
>
> A API principal é `GET /clareza/api/data` e `PUT /clareza/api/data`. O estado contém `transactions`, `incomes`, `cashClosings` e `settings`. O armazenamento usa MySQL quando `CLAREZA_DB_PASSWORD` existe e JSON local como fallback. No MySQL, `transactions` é a tabela consolidada de despesas e receitas; receitas usam `income_source_id`, despesas usam `expense_type_id`, `taker_id`, `location_id` e `creditor_id`. `cash_closings` referencia `payment_methods` e não deve ser confundida com lançamentos de `transactions`.
>
> Os catálogos são `expense_types`, `takers`, `locations`, `creditors`, `payment_methods` e `income_sources`. Quando aplicável, `display_order` define a ordem e `is_active` controla a disponibilidade em formulários e filtros. A interface mantém os nomes dos catálogos e `settings.catalogMetadata` separados; o backend deve inserir registros novos antes de atualizar Ordem/Status. A exclusão física só é permitida quando não existirem referências nas tabelas correspondentes; caso contrário, preserve o cadastro e informe o usuário.
>
> O Fechamento de Caixa usa somente formas de pagamento ativas, respeita `payment_methods.display_order`, impede duplicidade para a mesma data e gera a receita consolidada conforme as regras existentes. A ordenação por arraste altera apenas o estado local até o botão “Salvar Ordem” ser acionado. Ao investigar um problema, valide sempre o fluxo completo interface → payload da API → repositório MySQL → nova leitura, incluindo os formulários e as tabelas afetadas.
>
> Antes de alterar código, leia `src/server/database/repository.js`, `app.js`, `src/client/state-persistence.js`, `src/client/app-state.js`, `src/client/state-service.js`, `src/shared/registries.js` e os testes relacionados. Reutilize as regras existentes, não crie duplicidade entre `transactions` e `incomes`, não remova dados de produção e nunca versione credenciais, JSON de runtime, `dist/` ou `node_modules`. Execute `npm test`, `npm run build`, `node --check app.js`, `node --check server.js` e `git diff --check`. Alterações de banco devem ser integradas em `main` antes do deploy; publique somente pelo script oficial `.github/scripts/deploy.ps1`.
